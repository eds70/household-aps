## Как это работает

Лицензия — это **JWT-токен**, подписанный **ключом вендора**. Backend клиента проверяет его локально, **без обращения к серверам вендора** (offline-режим).

Состав JWT (payload):

| Поле | Что содержит | Обязательное |
|------|--------------|--------------|
| `iss` | `aps-scheduler-vendor` (фиксированный идентификатор) | да |
| `jti` | UUID лицензии (для будущего отзыва) | да |
| `holder` | Название организации-владельца | да |
| `tier` | `trial` / `community` / `enterprise` | да |
| `features` | Список активных фич (`audit_export`, `whatif`, `cz`, ...) | да |
| `iat` | Unix timestamp выпуска | да |
| `exp` | Unix timestamp истечения | да |
| `instance_id` | SHA256-хеш от железа сервера (опционально) | нет |
| `max_users` | Лимит пользователей (опционально) | нет |

**Два уровня защиты:**

- **Уровень 1 (подпись).** JWT подписан ключом вендора. Клиент может проверить подпись, но не может подписать свой токен — если только у него нет мастер-секрета (HS256) или приватного ключа (RS256).
- **Уровень 2 (привязка).** Если в JWT есть `instance_id`, backend проверяет, что текущий сервер имеет тот же `instance_id`. Лицензия не заработает на другом сервере.

## Для вендора

### Выбор алгоритма: HS256 vs RS256

| Критерий | HS256 | RS256 / ES256 |
|----------|-------|---------------|
| Тип ключа | Симметричный (один секрет) | Асимметричный (пара: приватный + публичный) |
| Кто может подписать лицензию | Любой, у кого есть секрет | Только владелец приватного ключа |
| Что передаётся клиенту | Тот же секрет | Только **публичный** ключ |
| Риск | Клиент может выпустить себе лицензию | Нулевой |
| Для чего | Локальная разработка | Продакшен |

**Правило:** на продакшене — только `RS256`. `HS256` — исключительно для dev, когда вендор и клиент — одно лицо.

### HS256 — для локальной разработки

```powershell
# Один раз — сгенерировать мастер-секрет
python backend\scripts\generate_license.py init-master-key --algorithm HS256
```

Создаст `~/.aps/license_master_key.hex` (64 hex-символа). Этот же ключ пойдёт в `.env` как `LICENSE_MASTER_SECRET`.

⚠️ **Не используйте HS256 в проде.** Клиент, зная секрет, может выпустить себе любую лицензию.

### RS256 — для продакшена

```powershell
# Один раз — сгенерировать пару ключей (RSA-3072)
python backend\scripts\generate_license.py init-master-key --algorithm RS256
```

Создаст два файла:

- `~/.aps/license_master_key.private.pem` — **секрет вендора**. Хранить только на машине вендора.
- `~/.aps/license_master_key.public.pem` — публичный ключ. Раздавать клиентам.

⚠️ Если приватный ключ утечёт — все выпущенные лицензии становятся недействительными только после смены ключа. См. [Ротация ключей](#ротация-ключей).

### Выпуск лицензии

```powershell
python backend\scripts\generate_license.py `
  generate `
  --algorithm RS256 `
  --org "ООО Ромашка" `
  --tier enterprise `
  --days 365 `
  --instance-id <instance_id_клиента> `
  --output romashka_2026.license
```

Параметры:

- `--org` — название организации (попадёт в `holder`).
- `--tier` — `trial` (для пилотов), `community` (базовый), `enterprise` (все фичи).
- `--days` — срок. Рекомендуется 365 для годовой подписки, 90 для триала.
- `--instance-id` — если клиент хочет привязку к своему серверу. **Опционально.** Клиент получает свой ID командой `instance-id` и присылает вам.
- `--features` — переопределить список фич (по умолчанию берётся по tier).
- `--max-users` — лимит пользователей (опционально).
- `--output` — сохранить JWT в файл.

На выходе — **LICENSE_KEY** (JWT-строка). Дальше — [письмо клиенту](#что-приходит-в-письме).

### Журнал выдачи

Каждая выпущенная лицензия автоматически записывается в CSV-журнал:

```
~/.aps/license_journal.csv
```

Колонки:

| Колонка | Что содержит |
|---------|--------------|
| `issued_at_utc` | Когда выпущена |
| `jti` | UUID лицензии |
| `algorithm` | HS256 / RS256 / ES256 |
| `holder` | Организация |
| `tier` | Уровень |
| `instance_id` | Привязка (если есть) |
| `max_users` | Лимит (если есть) |
| `expires_at_utc` | Когда истекает |
| `days` | Срок на момент выпуска |
| `output_file` | Куда сохранили JWT |
| `token_preview` | Первые 40 символов JWT |

Журнал **только append**. Для аудита — открывайте в Excel или pandas.

### Ротация ключей

**Когда менять ключ:**

- подозрение на утечку;
- увольнение сотрудника с доступом к приватному ключу;
- плановая ротация (раз в 2–3 года).

**Как менять (текущая реализация — один ключ):**

1. Сгенерировать новый ключ (или пару) в **отдельный файл**:
   ```powershell
   python backend\scripts\generate_license.py init-master-key --algorithm RS256 --master-key "$env:USERPROFILE\.aps\rsa_2027"
   ```
2. Перевыпустить лицензии **всем** активным клиентам с новым ключом.
3. Разослать новые `LICENSE_KEY` и `LICENSE_PUBLIC_KEY` вместе с инструкцией.
4. После подтверждения всеми клиентами — удалить старый ключ.

⚠️ Старые лицензии перестанут работать после того, как клиент сменит `LICENSE_PUBLIC_KEY`. Чтобы смягчить — заранее предупредите о дате отключения и дайте 30–60 дней переходного периода.

**Будущее:** поддержка нескольких публичных ключей одновременно (ротация без перевыпуска старых). Пока не реализована.

## Для клиента

### Что приходит в письме

Вендор присылает:

1. **LICENSE_KEY** — JWT-строку (начинается с `eyJ...`). Это сама лицензия.
2. **LICENSE_PUBLIC_KEY** — публичный ключ вендора (PEM-формат, начинается с `-----BEGIN PUBLIC KEY-----`). Используется для проверки подписи.
3. **Instance ID**, под который выпущена лицензия (если привязана). Клиент может сверить с `/api/v1/license/instance`.
4. Срок действия и уровень (`tier`).

### Установка лицензии

Открыть `backend\.env` и добавить:

```dotenv
LICENSE_VERIFY=true
LICENSE_KEY=eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOiJhcHMtc2NoZWR1bGVyLXZlbmRvciIsImp0aSI6Ij...

LICENSE_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----\nMIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...\n-----END PUBLIC KEY-----"
```

Формат `LICENSE_PUBLIC_KEY` — **любой из двух**:

**Вариант 1 — одна строка с литеральными `\n`:**

```dotenv
LICENSE_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----\nMIIB...\n-----END PUBLIC KEY-----"
```

Значение обязательно в **двойных кавычках**. `\n` — два символа: обратный слэш и `n`.

**Вариант 2 — многострочный, тоже в кавычках:**

```dotenv
LICENSE_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----"
```

Значение в **двойных кавычках**, с реальными переносами. Начинается с открывающей кавычки сразу после `=`, заканчивается закрывающей.

Оба варианта валидатор `normalize_pem` приводит к одному каноничному виду.

⚠️ **Не используйте `LICENSE_MASTER_SECRET` в продакшене.** Если вендор прислал публичный ключ — используйте `LICENSE_PUBLIC_KEY`. `LICENSE_MASTER_SECRET` — только для локальной разработки.

### Проверка

1. **Перезапустить backend:**
   ```bash
   docker compose -f docker-compose.prod.yml restart backend
   # или
   uvicorn app.main:app --host 0.0.0.0 --port 8000
   ```

2. **Проверить лог при старте.** Должно быть:
   ```
   [license] Режим проверки: RS256 (публичный ключ вендора)
   [license] Лицензия валидна: holder='ООО Ромашка', tier=enterprise, algorithm=RS256, expires=..., days_left=365, instance_bound=True
   ```

3. **Через API:**
   ```bash
   curl http://localhost:8000/api/v1/license/info
   ```

   Ожидаемо:
   ```json
   {"valid": true, "verify_enabled": true, "key_provided": true, "holder": "ООО Ромашка", "tier": "enterprise", "days_left": 365, "is_expired": false, "instance_bound": true}
   ```

4. **Через UI.** Открыть APS, посмотреть бейдж в шапке — должен быть **зелёный**: «Лицензия до DD.MM.YYYY».

## Диагностика

| Симптом в логе / UI | Причина | Решение |
|---------------------|---------|---------|
| `LICENSE_KEY не задан` | Пусто в `.env` | Проверить `backend\.env`, вставить ключ |
| `Не задан ключ для проверки подписи лицензии` | Задан `LICENSE_KEY`, но нет ни `LICENSE_PUBLIC_KEY`, ни `LICENSE_MASTER_SECRET` | Добавить `LICENSE_PUBLIC_KEY` (для RS256) |
| `Signature verification failed` | `LICENSE_PUBLIC_KEY` не соответствует подписи JWT | Перевыпустить лицензию или получить правильный публичный ключ |
| `Срок действия лицензии истёк` | Прошла дата `exp` | Запросить новую лицензию |
| `Лицензия привязана к другому серверу` | `instance_id` в JWT не совпадает с текущим | Запросить лицензию под текущий `instance_id` |
| `Проверка лицензии не прошла: ...` | Общая ошибка | Смотреть текст после двоеточия |
| UI показывает «Лицензия недействительна» | `/api/v1/license/info` вернул `valid: false` | Смотреть поле `error` в ответе |

**Получить свой instance_id:**

```bash
curl http://localhost:8000/api/v1/license/instance
```

Или через CLI:

```powershell
python backend\scripts\generate_license.py instance-id
```

## FAQ

**Клиент может выпустить себе лицензию?**

- С `RS256` — **нет**. У него только публичный ключ, подписать JWT нечем.
- С `HS256` — **да**, если узнает мастер-секрет. Поэтому HS256 только для dev.

**Что если приватный ключ утечёт?**

- Все лицензии, выпущенные этим ключом, **остаются валидными** — их подпись всё ещё правильная.
- Но кто угодно может **выпустить новые** лицензии от имени вендора.
- Действия: перевыпустить ключ, разослать новый `LICENSE_PUBLIC_KEY` клиентам, перевыпустить лицензии. См. [Ротация ключей](#ротация-ключей).

**Что если клиент переезжает на новый сервер?**

- Если лицензия **привязана** к `instance_id`: старая лицензия на новом сервере не сработает. Выпустить новую с новым `instance_id`.
- Если **не привязана**: просто скопировать `.env` на новый сервер. Всё заработает.

**Как отозвать лицензию до истечения срока?**

- **Сейчас:** никак. JWT — stateless. Единственный способ — сменить ключ.
- **В будущем:** поле `jti` уже в JWT, можно внедрить revocation list. Пока не реализовано.

**Сколько действует лицензия?**

- Настраивается при выпуске через `--days`. Рекомендуется 365 (годовая подписка), 90 (триал).
- Backend предупреждает в логе за 14 дней до истечения.

**Можно ли сделать лицензию бессрочной?**

- Технически — да, `--days 36500` (100 лет).
- Практически — не рекомендуется: сложно отзывать, теряется контроль.

## Для разработчика

### Файлы, относящиеся к лицензированию

| Файл | Что делает |
|------|------------|
| `backend/app/core/license.py` | Ядро: `verify_license`, `create_license_token`, `LicenseInfo`, `require_feature`, `require_tier`, `require_valid_license` |
| `backend/app/core/config.py` | Настройки: `LICENSE_KEY`, `LICENSE_PUBLIC_KEY`, `LICENSE_MASTER_SECRET`, `LICENSE_VERIFY` |
| `backend/app/main.py` | Middleware + startup: загрузка лицензии при старте, `LicenseMiddleware` для 403 на защищённых эндпоинтах |
| `backend/app/api/v1/license.py` | Публичные эндпоинты: `/api/v1/license/info`, `/api/v1/license/instance` |
| `backend/scripts/generate_license.py` | CLI для вендора: `init-master-key`, `generate`, `inspect`, `instance-id` |
| `frontend/src/pages/LicensePage.tsx` | UI статуса лицензии |
| `frontend/src/components/layout/MainLayout.tsx` | Бейдж лицензии в шапке |

### Поддерживаемые алгоритмы

Из `core/license.py`:

```python
SUPPORTED_ALGORITHMS: tuple[str, ...] = (
    "HS256", "HS384", "HS512",   # симметричные (dev)
    "RS256", "RS384", "RS512",   # RSA (prod)
    "ES256", "ES384", "ES512",   # ECDSA (prod)
)
```

`verify_license(key, secret, algorithm=None)` — если `algorithm=None`, принимает любой из `SUPPORTED_ALGORITHMS` и определяет по заголовку JWT. Это защищает от `alg=none` и algorithm confusion.

### Публичные эндпоинты (не требуют лицензии)

Из `core/license.py` — `PUBLIC_PATH_PREFIXES`:

- `/health`, `/docs`, `/redoc`, `/openapi.json`
- `/api/v1/auth/*` (login, me, change-password)
- `/api/v1/license/info`, `/api/v1/license/instance`

Всё остальное — блокируется `LicenseMiddleware` при `LICENSE_VERIFY=true` и невалидной лицензии.

```powershell
# Или вручную

```

```powershell

```
