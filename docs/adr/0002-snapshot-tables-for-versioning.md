# 0002. Snapshot tables for versioning

**Дата:** 2026-09-05
**Статус:** Принято
**Контекст:** Итерация 1

---

## Контекст

Система APS Production Scheduler строит планы производства, которые нужно **версионировать**:
- Пользователь может построить несколько планов.
- Планы нужно сравнивать между собой.
- Старые планы должны оставаться доступными для аудита.
- Каждый план должен быть **воспроизводимым** — зная входные данные, можно пересчитать результат.

**Что версионируется:**
- Расписание (`scheduled_task`).
- Справочники на момент построения плана (оборудование, рецептуры, операции).
- Календарь простоев.
- Смены.
- Настройки (см. [ADR 0003](0003-plan-settings-per-plan.md)).

**Проблема:**
Если справочники изменяются после построения плана, старый план становится невалидным:
- Нельзя воспроизвести результат.
- Нельзя сравнить два плана.
- Нельзя понять, почему задача была запланирована именно так.

**Пример:**
1. Построили план на 1 сентября.
2. 5 сентября изменили длительность операции `fill_LINE_1` с 120 на 150 минут.
3. Пересчитали план.
4. Старый план (от 1 сентября) теперь «ссылается» на операцию с новой длительностью — результат не воспроизводится.

---

## Решение

Использовать **снапшоты** (snapshot tables) для версионирования.

**Архитектура:**

```
schedule_version              — версия плана
    ├── id
    ├── organization_id
    ├── is_active             — активная версия (только одна)
    ├── parent_version_id     — родительская версия
    └── created_at

scheduled_task                — задача плана (снапшот)
    ├── id
    ├── schedule_version_id   — привязка к версии
    ├── batch_id
    ├── equipment_id
    ├── operation_name        — имя операции (снапшот)
    ├── start_at, end_at
    ├── shift_id
    ├── operator_pool
    ├── cooling_mode
    ├── is_pinned
    └── status
```

**Принципы:**

1. **Каждый план — отдельная версия.** При построении нового плана создаётся новая `schedule_version`, старые деактивируются (`is_active = FALSE`).

2. **Задачи хранят снапшот.** `scheduled_task` содержит все данные, необходимые для воспроизведения: `operation_name`, `start_at`, `end_at`, `operator_pool`, `cooling_mode`.

3. **Справочники не версионируются напрямую.** Вместо этого задачи хранят снапшот своих полей. Если справочник изменился — старые задачи не затрагиваются.

4. **Настройки версионируются через `plan_settings`.** См. [ADR 0003](0003-plan-settings-per-plan.md).

5. **`is_active` — только одна версия.** Активная версия — та, с которой работает UI по умолчанию.

**Hotfix Итерации 5:** при создании новой версии все старые деактивируются (`is_active = FALSE`). Иначе `shift.py` и `gantt.py` собирают задачи из всех версий → визуальное задвоение в 5–10 раз.

## Последствия

### Положительные

- ✅ **Воспроизводимость** — старый план всегда можно пересчитать.
- ✅ **Сравнимость** — можно сравнивать два плана.
- ✅ **Аудит** — история всех планов сохраняется.
- ✅ **Изоляция** — изменение справочника не ломает старый план.
- ✅ **Простота** — не нужно версионировать каждую таблицу справочника.
- ✅ **Гибкость** — можно добавить новые поля в снапшот.

### Отрицательные

- ⚠️ **Дублирование данных** — `operation_name` хранится в каждой задаче.
- ⚠️ **Размер БД** — растёт с каждой версией.
- ⚠️ **Нет автоматической синхронизации** — если справочник изменился, старые задачи не обновляются (это by design).
- ⚠️ **Нужно явно указывать `version_id`** — в API-эндпоинтах.

**Митигации:**
- `version_id` опционален в API — без него берётся активная версия.
- Старые версии можно удалять (`DELETE /api/v1/schedule/versions/{id}`).
- `ON DELETE CASCADE` — при удалении версии задачи удаляются.

### Альтернативы

#### 1. Soft-delete справочников

**Идея:** не удалять справочники, а помечать `is_deleted = TRUE` и добавлять `valid_from`, `valid_to`.

**Плюсы:**
- Нет дублирования данных.
- Единый источник правды.

**Минусы:**
- ❌ **Сложность запросов** — везде нужно учитывать `valid_from`/`valid_to`.
- ❌ **Сложность UI** — нужно показывать историю.
- ❌ **Не решает проблему полностью** — если изменили `operation_name`, старый план всё равно сломается.
- ❌ **Раздувание таблиц** — каждая версия справочника — новая строка.

**Почему отклонён:** сложность, не решает проблему полностью.

---

#### 2. Audit log

**Идея:** логировать все изменения справочников в отдельную таблицу.

**Плюсы:**
- Полная история изменений.
- Можно восстановить любое состояние.

**Минусы:**
- ❌ **Сложность** — нужно реализовать undo/redo.
- ❌ **Не решает проблему** — для воспроизведения плана нужно «отмотать» состояние на момент построения.
- ❌ **Дублирование** — audit log и справочники содержат одни и те же данные.

**Почему отклонён:** сложность, не решает проблему.

---

#### 3. Отдельная БД для каждого плана

**Идея:** каждый план — отдельная БД.

**Плюсы:**
- Полная изоляция.
- Нет дублирования.

**Минусы:**
- ❌ **Огромная сложность** — управление соединениями, миграции.
- ❌ **Не масштабируется** — 100 планов = 100 БД.
- ❌ **Проблемы с бэкапами** — нужно бэкапить каждую БД.

**Почему отклонён:** избыточно, не масштабируется.

---

#### 4. JSONB-поле со снапшотом

**Идея:** хранить снапшот справочника в JSONB-поле в `schedule_version`.

**Плюсы:**
- Простота.
- Гибкость.

**Минусы:**
- ❌ **Нет валидации** на уровне БД.
- ❌ **Сложность запросов** — JSONB не так удобен, как реляционные таблицы.
- ❌ **Нет индексов** на отдельные поля.
- ❌ **Проблемы с UI** — сложно отображать.

**Почему отклонён:** нет валидации, сложность запросов.

---

#### 5. Версионирование через `valid_from`/`valid_to` в каждой таблице справочника

**Идея:** каждая таблица справочника (equipment, operations, recipes) получает `valid_from`, `valid_to`.

**Плюсы:**
- Нет дублирования.
- Единый источник правды.

**Минусы:**
- ❌ **Сложность** — нужно везде учитывать временные интервалы.
- ❌ **Сложность запросов** — `WHERE valid_from <= :date AND valid_to > :date`.
- ❌ **Сложность UI** — нужно показывать историю.
- ❌ **Проблемы с производительностью** — индексы на временные интервалы.

**Почему отклонён:** сложность, не покрывает все случаи.
