# 0005. Help system as markdown articles

**Дата:** 2026-10-02
**Статус:** Принято
**Контекст:** Итерация 15.1

---

## Контекст

Пользователь, впервые открывший APS Production Scheduler, не понимает,
что делать. Техническая документация есть в `docs/*.md`, но она
**для разработчиков**: содержит SQL-запросы, миграции, детали API.
Конечному пользователю (планировщику, мастеру смены, лаборанту) она
не подходит.

**Что нужно:**

1. **Встроенная справка в UI** — пользователь открывает раздел
   «Помощь» и читает статьи по текущей задаче.
2. **Поиск по статьям** — быстрый доступ к нужной теме.
3. **Markdown-контент** — потому что:
    - статьи удобно писать и ревьюить в Git;
    - markdown-рендер в UI — стандарт;
    - можно ссылаться между статьями.
4. **Двухуровневая модель:**
    - **Глобальные статьи** (одинаковые для всех организаций) — базовые
      сценарии.
    - **Статьи организации** (per-organization) — кастомные инструкции
      для конкретного завода.
5. **Отдача `docs/*.md` через API** — чтобы UI мог показать
   техническую документацию без дублирования в БД.

**Ограничения:**

- Не хочется писать собственный markdown-редактор на фронте.
- Не хочется дублировать `docs/*.md` в БД.
- Нужно уложиться в 3 дня.

---

## Решение

Использовать **markdown-статьи в PostgreSQL** + **рендер через
`react-markdown`** + **отдача `docs/*.md` через API**.

### Схема БД

```sql
CREATE TABLE help_article (
    id UUID PRIMARY KEY,
    organization_id UUID REFERENCES organization(id) ON DELETE CASCADE,
    slug VARCHAR(100) UNIQUE NOT NULL,
    title VARCHAR(200) NOT NULL,
    category VARCHAR(50) NOT NULL,
    content_md TEXT NOT NULL,
    tags JSONB DEFAULT '[]'::jsonb,
    display_order INT DEFAULT 0,
    is_published BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ
);
```

**Ключевые решения по схеме:**

1. **`organization_id` nullable** — `NULL` = глобальная статья
   (одинаковая для всех). Не-NULL = статья конкретной организации.
2. **`content_md TEXT`**, а не `JSONB` — markdown хранится как строка,
   без экранирования. Это упрощает seed-миграции (используем
   dollar-quoted strings `$md$...$md$`).
3. **`slug VARCHAR(100) UNIQUE`** — человекопонятный URL вида
   `/help/intro-overview`.
4. **`tags JSONB`** — массив тегов для поиска. GIN-индекс.
5. **`display_order INT`** — порядок сортировки внутри категории.

### API

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/api/v1/help/articles` | Список статей (можно фильтровать по `category`) |
| `GET` | `/api/v1/help/articles/{slug}` | Одна статья с `content_md` |
| `GET` | `/api/v1/help/categories` | Список категорий с количеством |
| `GET` | `/api/v1/help/search?q=...` | Поиск по title / content / tags |
| `GET` | `/api/v1/help/docs/{filename}` | Отдача `docs/*.md` |

**Поиск** — простой `ILIKE` по `title ILIKE %q% OR content_md ILIKE %q%
OR tags::text ILIKE %q%`. Для продакшена можно заменить на
полнотекстовый `tsvector`, но для 15–50 статей этого достаточно.

**`/help/docs/{filename}`** — read-only отдача файлов из
`project_root/docs/`. Защита от path traversal, ограничение размера
1 МБ, только `.md`.

### Frontend

- **`react-markdown`** + **`remark-gfm`** — стандарт для рендера
  markdown в React.
- **`Allotment`** — двухпанельный layout (уже используется в проекте).
- **Внутренние ссылки** `/help/slug` перехватываются и открывают
  статью внутри приложения (без перезагрузки).
- **Поиск с debounce** 300 мс.

### Контент

15 стартовых статей в 8 категориях:

| Категория | Статей |
|-----------|--------|
| `getting-started` | 2 |
| `planning` | 4 |
| `gantt` | 4 |
| `shift` | 1 |
| `lab` | 1 |
| `cz` | 1 |
| `whatif` | 1 |
| `settings` | 1 |

Заполняются через seed-миграции `add_24_seed_1.sql` (3 статьи),
`add_24_seed_2.sql` (5), `add_24_seed_3.sql` (7). Идемпотентны
(`ON CONFLICT (slug) DO NOTHING`).

## Последствия

### Положительные

- ✅ **Markdown** — стандарт для контента, легко ревьюить в Git.
- ✅ **Единый источник правды** для UI-справки — таблица
  `help_article`.
- ✅ **Двухуровневость** — глобальные + per-org статьи.
- ✅ **`docs/*.md` отдаётся как есть** — не дублируется в БД.
- ✅ **Seed-миграции** — контент в Git, а не «где-то в БД».
- ✅ **Простой поиск** через `ILIKE` — достаточно для 15–50 статей.
- ✅ **`react-markdown`** — 98 пакетов, из них большинство — уже
  в проекте через MUI (через `unified`).
- ✅ **Обратная совместимость** — эндпоинты read-only, не ломают
  существующие модули.
- ✅ **Расширяемость** — можно добавлять новые категории и статьи
  без миграций (через API на будущих итерациях).

### Отрицательные

- ⚠️ **`organization_id` не используется в UI** — все статьи
  сейчас глобальные. Per-org статьи — на будущее.
- ⚠️ **`\r\n` в `content_md`** — seed-файлы применялись через
  PowerShell, что добавило `\r` в line endings. На рендер не
  влияет, но при желании можно почистить `REPLACE(content_md, E'\r\n', E'\n')`.
- ⚠️ **Поиск неполнотекстовый** — при 100+ статьях станет медленным.
  Тогда — `tsvector` + GIN.
- ⚠️ **Нет редактирования статей через UI** — только чтение. Для
  правок — SQL или seed-миграции.
- ⚠️ **`react-markdown` не поддерживает raw HTML** без
  `rehype-raw` — если понадобится, добавим отдельно.
- ⚠️ **Внутренние ссылки не валидируются** — если в статье ссылка
  на несуществующий slug, будет 404.

**Митигации:**

- `\r\n` — исправляем через `UPDATE`, не критично.
- Поиск — легко мигрировать на `tsvector` в следующей итерации.
- Редактирование — отдельная под-итерация 15.5, если понадобится.
- Валидация ссылок — можно добавить проверку при загрузке статьи.

### Альтернативы

#### 1. Хранить статьи как статические файлы во frontend

**Идея:** `frontend/src/help/*.md`, импорт через Vite.

**Плюсы:**
- Не нужна БД.
- Не нужен API.

**Минусы:**
- ❌ **Нельзя редактировать без пересборки frontend.**
- ❌ **Нельзя добавить per-org статьи.**
- ❌ **Поиск на фронте** — медленно, без индексов.
- ❌ **Нет версионирования контента** отдельно от кода.

**Почему отклонён:** нужна гибкость, которой нет у статики.

---

#### 2. Внешняя wiki (Confluence, Notion)

**Идея:** ссылки на внешнюю wiki.

**Плюсы:**
- Готовый редактор.
- Красивый UI.

**Минусы:**
- ❌ **Требует внешней системы.**
- ❌ **Нет интеграции с UI** (отдельный сайт).
- ❌ **Нельзя искать из приложения.**

**Почему отклонён:** не решает задачу «встроенная справка».

---

#### 3. JSON-контент вместо markdown

**Идея:** структурированный JSON (заголовки, абзацы, таблицы).

**Плюсы:**
- Полный контроль над рендером.
- Легко валидировать.

**Минусы:**
- ❌ **Неудобно писать** — многословно.
- ❌ **Нет привычной разметки.**
- ❌ **Сложные таблицы и код** — громоздко.

**Почему отклонён:** markdown удобнее для контента.

---

#### 4. Редактор WYSIWYG в UI

**Идея:** писать статьи прямо в UI (TipTap, Slate, Lexical).

**Плюсы:**
- Удобно для не-технических пользователей.
- Не нужен Git.

**Минусы:**
- ❌ **Огромный объём работы** — нужен редактор, превью,
  валидация, версионирование.
- ❌ **Не влезает в 3 дня.**
- ❌ **Контент в БД без Git-истории.**

**Почему отклонён:** не для 15.1. Возможная под-итерация 15.5.

---

#### 5. Генерация PDF/статики на этапе сборки

**Идея:** pre-render markdown в HTML при сборке.

**Плюсы:**
- Быстрый рендер.
- Нет динамики.

**Минусы:**
- ❌ **Нельзя менять без пересборки.**
- ❌ **Нет поиска по свежим статьям.**
- ❌ **Per-org статьи невозможны.**

**Почему отклонён:** та же проблема, что у статики.
