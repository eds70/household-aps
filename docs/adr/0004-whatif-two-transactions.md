# 0004. What-if two transactions

**Дата:** 2026-09-24
**Статус:** Принято
**Контекст:** Итерация 12

---

## Контекст

Система APS Production Scheduler должна поддерживать **what-if сценарии** — запуск альтернативных планов с изменениями (заказы, режим смен, capacity, календарь) **без изменения основной БД**.

**Что нужно:**
- Пользователь создаёт сценарий с изменениями.
- Система запускает планировщик с этими изменениями.
- Результат сохраняется как **отдельная** `schedule_version`.
- Основная БД (заказы, capacity, календарь) **не меняется**.
- Можно сравнить base vs result.

**Пример:**
1. Есть активный план (base).
2. Пользователь создаёт сценарий: «Авария Р4 (25–28.09)».
3. Система:
    - Применяет изменения (добавляет `calendar_event` для Р4).
    - Запускает планировщик.
    - Получает результат.
    - **Откатывает** изменения.
    - Сохраняет результат как отдельную `schedule_version`.
4. Пользователь сравнивает base vs result.

**Проблема:**
Как применить изменения, запустить планировщик и **гарантированно** откатить изменения?

**Требования:**
- Rollback 100% надёжен.
- Изменения видны планировщику (он читает из БД).
- Результат сохраняется отдельно.
- Не блокирует БД надолго.
- Работает с async SQLAlchemy.

---

## Решение

Использовать **архитектуру 2 транзакций**:

### Транзакция №1 — rollback (применение изменений)

```python
async with session.begin():  # Транзакция №1
    # 1. Применяем изменения
    await self._apply_changes(scenario.changes)

    # 2. Запускаем планировщик
    scheduler = ProductionScheduler(
        session=session,           # та же сессия!
        version_id=base_version_id,
    )
    result = await scheduler.build_schedule()

    # 3. Получаем результат в памяти
    tasks = result.tasks
    metrics = self._compute_metrics(result)

    # 4. Rollback (явно или через исключение)
    raise RollbackTransaction()
```

**Ключевое:**
- Планировщик получает **ту же сессию**, что и изменения.
- Планировщик **видит незакоммиченные изменения** (они в той же транзакции).
- После получения результата — **rollback**.
- Изменения **не попадают** в БД.

### Транзакция №2 — commit (сохранение результата)

```python
async with session.begin():  # Транзакция №2 (новая)
    # 1. Создаём новую schedule_version
    saver = ScheduleSaver(session=session, _owns_session=False)
    await saver.save(
        result=tasks,
        name=f"What-if: {scenario.name}",
        parent_version_id=base_version_id,
    )

    # 2. Commit — результат сохраняется
```

**Ключевое:**
- Новая транзакция — изменения из Транзакции №1 уже откачены.
- Сохраняется только результат.
- `ScheduleSaver` не делает commit при `_owns_session=False`.

### Схема

```
┌─────────────────────────────────────────────────────────────────┐
│ Транзакция №1 (rollback)                                        │
│                                                                 │
│  BEGIN                                                          │
│    ├── _apply_changes(changes)                                  │
│    │     ├── shift_mode = "3x8"                                 │
│    │     ├── resource_capacity.REACTOR_OPERATOR = 5             │
│    │     └── calendar_events: add BREAKDOWN для Р4              │
│    │                                                            │
│    ├── ProductionScheduler(session).build_schedule()            │
│    │     └── result = { tasks, metrics }                        │
│    │                                                            │
│    └── ROLLBACK                                                 │
│          └── изменения откачены                                 │
│                                                                 │
│  (в БД: shift_mode = "1x8", capacity = 3, нет BREAKDOWN)        │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ Транзакция №2 (commit)                                          │
│                                                                 │
│  BEGIN                                                          │
│    ├── ScheduleSaver(session, _owns_session=False).save(        │
│    │       result=tasks,                                        │
│    │       name="What-if: Авария Р4",                           │
│    │       parent_version_id=base_version_id                    │
│    │   )                                                        │
│    │                                                            │
│    └── COMMIT                                                   │
│          └── результат сохранён как новая schedule_version      │
│                                                                 │
│  (в БД: новая schedule_version с задачами)                      │
└─────────────────────────────────────────────────────────────────┘
```

### Ключевые компоненты

**`WhatIfRunner`** (`backend/app/scheduler/whatif.py`):
- `create_scenario`, `get_scenario`, `list_scenarios`, `update_scenario`, `delete_scenario`.
- `run_scenario` — запуск (async через BackgroundTasks).
- `compare` — сравнение base vs result.
- `_apply_changes` — оркестрация применения изменений.
- `_apply_shift_mode`, `_apply_capacity_changes`, `_apply_order_changes`, `_apply_calendar_changes`.
- `_compute_metrics` — 6 метрик для сравнения.

**`ProductionScheduler`** — принимает `session` извне (не создаёт свою).

**`ScheduleSaver`** — принимает `session`, не делает commit при `_owns_session=False`.

**`DataLoader`** — принимает `session` извне.

### Типы изменений

| Тип | Что меняет |
|-----|------------|
| `add_order` | Добавляет заказ |
| `cancel_order` | Отменяет заказ |
| `change_qty` | Меняет объём партии |
| `change_due_date` | Меняет срок |
| `shift_mode` | Меняет режим смен |
| `resource_capacity` | Меняет capacity пула |
| `calendar_events` | Добавляет/удаляет события календаря |

### Async запуск

- `POST /run` возвращает `202 Accepted` сразу.
- Расчёт в `BackgroundTasks` (отдельная сессия БД).
- Frontend polling через `GET /scenarios/{id}` каждые 3 сек.
- Статусы: `DRAFT` → `RUNNING` → `DONE`/`FAILED`.

### Итерация 13.14: `version_id`

`ProductionScheduler` в what-if получает `version_id=base_version_id` — использует настройки **базового плана**, а не глобальные. Это гарантирует корректность сравнения метрик base vs result.

## Последствия

### Положительные

- ✅ **Rollback 100% надёжен** — изменения не попадают в БД.
- ✅ **Планировщик видит изменения** — та же сессия, та же транзакция.
- ✅ **Не блокирует БД надолго** — 2 короткие транзакции.
- ✅ **Работает с async SQLAlchemy** — `async with session.begin()`.
- ✅ **Результат сохраняется отдельно** — новая `schedule_version`.
- ✅ **Сравнимость** — 6 метрик для base vs result.
- ✅ **Не требует копирования данных** — изменения применяются «на лету».
- ✅ **Async** — не блокирует API.

### Отрицательные

- ⚠️ **Сложность** — 2 транзакции, нужно следить за сессией.
- ⚠️ **Планировщик должен принимать `session`** — не создавать свою.
- ⚠️ **`ScheduleSaver` не должен делать commit** при `_owns_session=False`.
- ⚠️ **`shift_regenerator`** — `flush()` вместо `commit()`.
- ⚠️ **SQLAlchemy async** — автоматически начинает транзакцию, нельзя явно `begin()`.
- ⚠️ **Ошибки в Транзакции №1** — нужно корректно обрабатывать.

**Митигации:**
- Явный `_owns_session` флаг.
- `flush()` вместо `commit()` в `shift_regenerator`.
- Тесты на rollback (45 тестов в `test_whatif.py`).
- Логирование всех шагов.

### Альтернативы

#### 1. Savepoint

**Идея:** использовать savepoint внутри одной транзакции.

```python
async with session.begin():
    savepoint = await session.begin_nested()
    try:
        await self._apply_changes(changes)
        result = await scheduler.build_schedule()
    finally:
        await savepoint.rollback()
```

**Плюсы:**
- Одна транзакция.
- Проще.

**Минусы:**
- ❌ **Не работает с async SQLAlchemy** в нужном объёме.
- ❌ **Savepoint не всегда откатывает всё** — некоторые операции (DDL) не откатываются.
- ❌ **Сложность с вложенными транзакциями**.
- ❌ **Проблемы с `flush()`** — изменения могут «протечь».

**Почему отклонён:** не работает с async SQLAlchemy, ненадёжен.

---

#### 2. Отдельная БД для what-if

**Идея:** копировать БД в отдельную, применять изменения там.

**Плюсы:**
- Полная изоляция.
- Rollback не нужен.

**Минусы:**
- ❌ **Огромная сложность** — копирование БД.
- ❌ **Медленно** — копирование занимает время.
- ❌ **Не масштабируется** — 100 сценариев = 100 БД.
- ❌ **Проблемы с бэкапами**.

**Почему отклонён:** избыточно, медленно.

---

#### 3. Копирование данных в памяти

**Идея:** загрузить все данные в память, применить изменения там.

**Плюсы:**
- Нет транзакций.
- Быстро.

**Минусы:**
- ❌ **Сложность** — нужно копировать все справочники.
- ❌ **Проблемы с согласованностью** — данные могут измениться.
- ❌ **Память** — при большом объёме данных.
- ❌ **Дублирование логики** — `DataLoader` + копирование.

**Почему отклонён:** сложность, дублирование логики.

---

#### 4. Временные таблицы

**Идея:** создавать временные таблицы для what-if.

**Плюсы:**
- Изоляция.
- Rollback через `DROP TABLE`.

**Минусы:**
- ❌ **Сложность** — нужно дублировать схему.
- ❌ **Проблемы с внешними ключами**.
- ❌ **DDL в транзакции** — не всегда откатывается.
- ❌ **Сложность с async SQLAlchemy**.

**Почему отклонён:** сложность, DDL в транзакции.

---

#### 5. Soft-delete + audit log

**Идея:** не удалять данные, а помечать `is_deleted` + логировать изменения.

**Плюсы:**
- Нет rollback.
- Полная история.

**Минусы:**
- ❌ **Сложность запросов** — везде учитывать `is_deleted`.
- ❌ **Сложность UI** — нужно показывать историю.
- ❌ **Раздувание таблиц**.
- ❌ **Не решает проблему** — what-if изменения всё равно нужно применять.

**Почему отклонён:** сложность, не решает проблему.

---

#### 6. Отдельная схема PostgreSQL

**Идея:** создавать отдельную схему (`schema`) для каждого what-if.

**Плюсы:**
- Изоляция.
- Rollback через `DROP SCHEMA`.

**Минусы:**
- ❌ **Сложность** — нужно дублировать схему.
- ❌ **Проблемы с внешними ключами** между схемами.
- ❌ **DDL в транзакции**.
- ❌ **Сложность с async SQLAlchemy**.

**Почему отклонён:** сложность, DDL в транзакции.
